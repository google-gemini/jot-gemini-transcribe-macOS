## 3. [high] RetryQueue treats all .network/.timeout as 'still offline': permanent failures retry forever and head-of-line-block the whole queue
**File**: JotCore/Sources/HistoryStore/RetryQueue.swift (105-115)

RetryQueue.process maps .offline, .network, and .timeout all to .stillOffline, which (a) leaves the record's status untouched so it stays retryable forever (no attempt counter, no 24h cap as the failure-matrix timeout policy requires), and (b) causes drain() (lines 49-59) to return immediately, pausing the ENTIRE drain. But TranscriptionError.network covers permanent HTTP failures too: GeminiClient's default branch maps 400 (malformed/oversized request) and 404 (renamed/dead model override — explicitly anticipated in GeminiConfig's own doc comment) to .network. HistoryStore.retryableRecords (HistoryStore.swift:160-168) additionally includes failed records with errorCode network/timeout, so coordinator-failed sessions re-enter this loop as well. A realistic internal trigger exists: a crash-truncated/empty CAF queued by RecoveryScanner encodes to a tiny FLAC that the API 400s permanently. 

**Fix**: Carry the HTTP status in TranscriptionError (e.g. .http(status, message)) and map only genuine transport-level errors to the still-offline path; treat 4xx as permanent (mark failed, drop from queue) and 5xx/timeout as transient with a per-record attempt count + 24h cap persisted in meta. In drain(), 'continue' past a record that failed with a non-offline error instead of returning, so one bad record cannot block the queue.

**Fix assessment**: Directionally correct and workable. Carrying HTTP status in TranscriptionError (e.g. .http(status, message)) and mapping only transport-level URLError cases to the still-offline path fixes the misclassification; changing drain() to 'continue' past non-offline failures fixes head-of-line blocking (keep 'return' only for genuine .offline). ## 7. [high] Crash-recovered sessions transcribe with durationSeconds 0 — 30s deadline makes long recordings unrecoverable and can poison the retry queue

A session interrupted while status=recording never had audioDurationSeconds written (the coordinator sets it only at finalize, DictationCoordinator.swift:152-156). RecoveryScanner passes `meta.audioDurationSeconds ?? 0` and RetryQueue passes the same, so TimeoutPolicy.overallDeadline(0) = 30s is applied regardless of actual audio length.
