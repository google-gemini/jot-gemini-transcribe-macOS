# Adversarial Critique

## Must-fix list

### 1. [critical] CONTRADICTION — hands-free lock gesture. Architecture's HotkeyProcessor: press <0.3s = toggle-lock (Hex grammar). Experience + Product: double-tap = lock, and short tap shows 'Hold to talk — double-tap to lock' coaching. These are mutually exclusive; under the arch spec the coaching state can never occur because a short tap already locks, and grazing the fn key starts a phantom recording.
**Fix:** Adopt the Wispr grammar (research documents it as the loved interaction): hold = PTT, double-tap (~350ms window) = lock, single short tap = coaching hint with audio silently discarded, Esc = cancel. Rewrite HotkeyProcessor spec + its test matrix before M1. Same item: Experience S6 offers 'Hold right ⌘' — a bare modifier KeyboardShortcuts cannot capture; either route all bare-modifier presets through the existing CGEventTap flagsChanged path or cut the right-⌘ preset.

### 2. [critical] CONTRADICTION — recording cap and chunking. Architecture: 30-min cap, warning at 28, ChunkPlanner splits >8-min dictations at silence boundaries in v1 (M8). Product: 9:00 soft / 10:00 hard cap, chunking explicitly v1.x. Both caps derive from a 20MB inline limit neither has verified.
**Fix:** Adopt the 10-min cap and delete ChunkPlanner, silence-boundary scanning, and multi-request continuity prompts from v1 entirely (clear over-engineering: sequential chunked requests multiply every failure mode in the matrix). Derive the final cap constant from the measured request-size limit in the endpoint spike, not from assumed 20MB.

### 3. [critical] CONTRADICTION + unvalidated product-defining assumption — streaming transcript preview in the HUD. Product lists it as a v1 feature and perceived-speed trick #3; the Experience plan's pill has NO text-preview state (processing pill is 132pt wide, physically cannot show text) and its own risks call the preview a 'future experiment'. Research (gap-llm-cleanup) warns token streaming for short outputs arrives in 75–180ms — effectively one lump — and TTFT dominates, so the preview may be visually meaningless even if SSE is incremental.
**Fix:** Gate on the endpoint spike (does streamGenerateContent emit incremental chunks for audio, and what is TTFT?). If genuinely incremental and TTFT <1s: design the missing HUD state now — pill expands into a transcript strip, replace-not-append rendering per the research's stuttering-duplicates warning. If not: cut the preview from v1, rewrite Product §5.3's latency story around choreography + earcons, and accept that p50 ≤0.9s may need revising. Decide before the HUD design freezes at M5.

### 4. [high] CONTRADICTION with a correctness bug hiding in it — clipboard restore delay. Architecture restores the pasteboard 300ms after synthetic ⌘V; Product F16/F24 says 3s. If restore fires before a slow app (Electron under load, Java IDEs, remote-desktop) actually reads the pasteboard on paste, the app pastes the user's OLD clipboard instead of the transcript — silently inserting wrong text, the worst possible failure for a dictation app.
**Fix:** One constant, one owner: restore at ~1s default, but only after paste verification (AX value read-back or app-activation heuristic) where available; keep the changeCount + session-UUID guard; allow per-app delay override in AppQuirksTable. Add the paste-read-latency probe (spike list) to pick the number empirically rather than splitting the difference.

### 5. [high] MISSING MODULE — offline/persistent retry queue. Product F1/F5/F6 and the Experience offline state require NWPathMonitor, a persisted queue that survives relaunch, auto-drain on network-restored, and an amber queued-badge. The Architecture plan has none of this: its RetryPolicy is one silent retry then terminal error with manual History retry. The magic-checklist item 9 ('Wi-Fi on → it lands by itself') is unimplementable as architected.
**Fix:** Add a RetryQueue module to TranscribeCore (GRDB-backed status column + NWPathMonitor; drain on path-satisfied and on launch). Simultaneously CUT the product plan's 0.5s/30s/2m/10m jittered ladder with 24h horizon — over-engineered; v1 policy = one immediate silent retry, then drain-on-network-change + manual Retry. Never auto-insert drained results (focus is gone); notify + History, matching F14's own logic.

### 6. [high] CONTRADICTION + implementation gap — mic device policy mid-recording. Architecture: follow the default device, full engine rebuild, keep appending (AirPods-follows-default). Product F13: input pinned at session start, new devices ignored, fall back to built-in only if the pinned device vanishes. Also unstated: AVAudioEngine's inputNode follows the system default by design — pinning requires setting kAudioOutputUnitProperty_CurrentDevice on the input node's audio unit, which nobody has specced or tested.
**Fix:** Adopt F13's pinning (it kills the AirPods-HFP-garble class Wispr suffers, and mid-sentence device switches are almost never what the user wants). Spec the AU-level device pinning in AudioCaptureEngine, keep the rebuild+gap-marker path for pinned-device-vanished, and add a 30-minute spike to confirm pinning + vanish behavior before M2.

### 7. [medium] CONTRADICTION — HUD lifecycle ownership. Architecture's state machine auto-hides the HUD 1.5s after done and has no idleDot concept; Experience defaults to an always-visible idle dot, 700ms success dwell, 6s error auto-dismiss, hover-interactive states (which also contradicts arch's 'ignoresMouseEvents unless chip shown'). Related: secureField policy is three-way inconsistent — arch/experience block recording at hotkey-down, Product F18 implies a transcript exists and lands in History.
**Fix:** Declare Experience §1.3/§1.6 canonical for every HUD state, timing, and mouse-interactivity rule; the coordinator emits semantic states only and the HUD maps them (delete arch's 1.5s auto-hide row and its HUD side-effect column details). For secure input: adopt block-at-start (no recording, 2.5s toast); F18's text-in-History branch applies only when secure input engages mid-session.

### 8. [medium] CONTRADICTION + silent-cost bug — crash recovery. Architecture RecoveryScanner: manual 'Recovered — Retry' rows. Product F14: auto-transcribe all recovered audio on launch. Auto-transcribing N stale folders silently spends the user's BYOK quota (free-tier users hit daily limits, F5's own top risk) and can burn money on week-old accidental recordings.
**Fix:** Auto-transcribe only the most recent recovered dictation (the one the user actually lost mid-flow) + notification; older recovered folders get manual 'Recovered — Retry' rows. Never auto-insert. Write the merged behavior into both RecoveryScanner and F14.

### 9. [medium] CONTRADICTION — two competing 'single sources of truth' for timeouts, plus a broken formula. Arch: stall 15s, overall max(60s, 2× audio duration). Product: stall 10s, overall max(30s, 2× duration), slow-state 3s; Experience says slow-state at >4s. The 2×duration formula yields a 20-MINUTE hang allowance for a 10-min dictation — two orders of magnitude beyond any real server time (upload ~6s + TTFT ~2s + decode ~7s).
**Fix:** One TimeoutPolicy.swift both plans cite: connect 5s, TTFB 10s, inter-chunk stall 10s, overall = 30s + audioDuration/4 (≈2.5 min worst case for 10-min audio), slow-state UI at 3s. Delete the arch table's numbers and the Experience '>4s' figure.

### 10. [medium] PRIVACY CONSISTENCY + settings-scope contradiction. Product §3.1 step 1 captures ≤200 chars of cursor context unconditionally, while its own PRIVACY.md §2 says cursor context is 'off by default', and Architecture's PromptAssembler has no cursor-context input at all — the app's core positioning is privacy, so shipping a doc that contradicts the pipeline is fatal to trust. Separately, Product's 'tone category editor' in Settings contradicts Experience's locked 4-tab, no-editors IA.
**Fix:** Ship cursor-context OFF by default behind the documented toggle; gate pipeline step 1 and the §3.7 step-5 insertion-glue on it; add the optional field to PromptAssembler. Cut the tone-category editor from v1 — ship a fixed, authored default bundle-ID→category map (iMessage/Slack/Mail/Terminal/VS Code etc. — this table doesn't exist yet in any plan and magic-checklist #6 depends on it) with 'Other' fallback.

### 11. [high] SHIP BLOCKER (process) — brand/legal exposure. The four-color processing sweep, AI-shimmer edge glow, G-major 'Super G lineage' earcons, and 'unmistakably Google' positioning, shipped as unofficial OSS by a Google employee, sit adjacent to protected brand assets. Google Sans Flex's OFL status is unverified with no upstream repo (google/fonts #10006/#10077). All three plans flag this; none makes it a gate.
**Fix:** Make internal OSS/brand/legal review an explicit exit criterion for M8 (repo cannot go public without it) and start the process at M0 — it has weeks of lead time. Pin the exact font binary + OFL text in-repo now. Prepare the fallback: neutral accent palette + Roboto Flex + non-quad processing treatment, so a 'no' costs a re-skin, not a redesign.

### 12. [medium] OVER-ENGINEERING + shaky technical claim — encode-while-speaking. Product §5.3 claims incremental FLAC + base64 during the hold yields a request body 'ready in ~10ms' at key-up. FLAC finalizes its STREAMINFO header (total samples + MD5) at close, so the base64 prefix computed mid-hold is invalidated; AVAudioFile's kAudioFormatFLAC write path is unverified for this. Additional v1 fat: the optional CleanupPass second-model code path (off by default but fully built, tested, gated), milestone confetti/streak toasts (Experience's own risk list calls them gimmick-prone), and the draggable idle-dot snap zones.
**Fix:** Cut incremental b64: encode CAF→FLAC and base64 once at key-up (~100–200ms for even 10-min audio — invisible inside the budget); validate the AVAudioFile FLAC write in the spike. Delete CleanupPass code from v1 (keep the Settings stub marked v1.x). Defer streaks/milestone confetti and dot-dragging to v1.x; keep word-count-under-checkmark and the onboarding confetti.

## Spikes needed
- Endpoint reality probe (day 1, throwaway CLI, gates must-fix #2/#3/#9/#12): does gemini-3.5-transcribe-preview accept FLAC in inline_data; actual request-size ceiling (binary-search with padded audio); is SSE output genuinely incremental for audio or one lump; TTFT p50/p95 for 5s/30s/5min clips; are temperature=0, thinking-disable, audioTranscriptionConfig, and BLOCK_NONE safetySettings honored; 429 retryDelay shape and real free-tier RPM/RPD under dictation-like load.
- fn-key CGEventTap probe on macOS 14/15/26: consuming flagsChanged keycode-63 and whether it suppresses the system globe action at default AppleFnUsageType; tap survival under kill -STOP/timeout; whether flagsChanged still arrives during secure input; whether Sequoia/Tahoe demand Input Monitoring separately from Accessibility for keyboard taps; Tahoe CGPreflightPostEventAccess + synthetic Cmd-V acceptance (the whole Tier-2 ladder).
- AVAudioFile FLAC-write probe: kAudioFormatFLAC 16kHz mono into a .flac container — does it work at all, encode time for 10-min audio at key-up, and is the produced file accepted by the endpoint (feeds probe 1).
- Electron/Chromium AX insertion probe (Slack, VS Code, Chrome + Google Docs): AXManualAccessibility first-set latency (can be seconds on big apps), kAXSelectedTextAttribute write + read-back verification truthfulness — decides Tier-1 viability, the AppQuirksTable seed, and v1.1 auto-learn coverage.
- Mic-pinning probe: kAudioOutputUnitProperty_CurrentDevice on AVAudioEngine's inputNode — does pinning hold across route changes, and what happens when the pinned device (AirPods) vanishes mid-tap.
- Paste-read-latency probe: instrument how late slow apps (Electron under load, Java IDEs, remote desktop) actually read NSPasteboard after a synthetic Cmd-V — sets the restore-delay constant in must-fix #4 empirically.

## Build order verdict
APPROVE architecture's M0–M8 sequence with amendments — do not start M1 until two things exist. (1) The endpoint reality probe moves from M3 to week zero: it is the single riskiest unknown and silently gates the recording cap, chunking decision, streaming-preview design, latency targets, and timeout formula — building M1/M2 while it runs in parallel is fine, but the HUD and product copy must not be designed against unverified API behavior. (2) A one-page spec-reconciliation doc resolving the divergences above (hotkey grammar, cap, timeouts, clipboard delay, HUD lifecycle, device pinning, crash recovery, cursor-context default) — right now the three plans would have three engineers building three different apps; every contradiction found here is cheap to fix on paper and expensive at M5. Additional amendments: adopt the architecture plan's repo layout (single TranscribeCore package) as canonical — the product plan's Packages/Core* split and the experience plan's Sources/App/ paths must be updated to match; keep Tahoe paste validation inside M4 as planned; DesignTokens/MotionTokens can land at M0 in parallel, but freeze the HUD processing-state design only after probe 1 answers the streaming question; M6 absorbs the new RetryQueue module; brand/legal review starts at M0 and is an M8 exit criterion. The underlying risk-first ordering (hotkey → crash-safe audio → transcription → insertion → polish → history → onboarding → hardening) is correct: each milestone retires the top field-failure class of the apps this product is trying to beat before any polish is layered on, and M4 as 'first end-to-end dictation' is the right integration checkpoint.
