# Research: Wire protocol and client network engineering for sub-second streaming speech-to-text
# Transport & Wire-Format Research for macOS Push-to-Talk Dictation Client

## 1. Protocol comparison

### Raw WebSocket (RFC 6455 over TLS/443) — RECOMMENDED
- **This is what nearly every production streaming STT vendor ships**: Deepgram (`wss://api.deepgram.com/v1/listen`), AssemblyAI Universal-Streaming (`wss://streaming.assemblyai.com/v3/ws`), Soniox (`wss://stt-rt.soniox.com/transcribe-websocket`), OpenAI Realtime (`wss://api.openai.com/v1/realtime`). Only Google Cloud STT uses gRPC (and streaming is gRPC-only in their API — no REST equivalent).
- Universal pattern: **binary frames = audio, text frames = JSON control/results**. Deepgram explicitly warns KeepAlive must be a *text* frame; binary-encoded JSON can be misinterpreted as audio (DATA-0000 close).
- Connect cost from cold: DNS + TCP (1 RTT) + TLS 1.3 (1 RTT) + HTTP Upgrade (1 RTT) ≈ 3 RTTs (~90–200 ms on typical links) — motivates pre-warming (section 3).
- Traverses corporate proxies far better than gRPC/WebTransport because it starts as HTTPS on 443.

### Apple-platform WebSocket client pitfalls
- **URLSessionWebSocketTask silent-drop issue (confirmed by Apple DTS)**: after network loss, `send()` continues reporting success for 40+ s; error surfaces only after 60 s–3 min via TCP timeout; `sendPing` produces no pong and no prompt error; no config (`timeoutIntervalForRequest`, `networkServiceType`) helps. Apple DTS (Matt Eaton) recommendation: use **Network.framework** instead, and always keep a `receive()` loop pending since receive failure is the fastest error signal (https://developer.apple.com/forums/thread/678384).
- Other URLSessionWebSocketTask quirks: `receive()` delivers exactly one message and must be re-armed (recursive loop); `maximumMessageSize` defaults to 1 MB; `sendPing` pongReceiveHandler can be **called twice** when connection cancels right after ping (Apple bug r.129686846) — crashes naive `withCheckedThrowingContinuation` wrappers (https://forums.developer.apple.com/forums/thread/756482); no async `sendPing`; ping payload not customizable (https://www.appspector.com/blog/websockets-in-ios-using-urlsessionwebsockettask).
- **Recommended client stack: Network.framework `NWConnection` + `NWProtocolWebSocket`** (macOS 10.15+): immediate `.waiting`/`.failed` state updates, `viabilityUpdateHandler`, `betterPathAvailableHandler`, configurable TCP keepalive (`NWProtocolTCP.Options.enableKeepalive`, `keepaliveIdle`), `connectionDropTime`/`noDelay`, and TLS control. This directly fixes the silent-drop failure mode.

### gRPC bidirectional streaming (HTTP/2)
- grpc-swift-2 released 2025-02-14 (https://www.swift.org/blog/grpc-swift-2/, https://github.com/grpc/grpc-swift-2): full async/await, all four call types incl. bidi streaming, HTTP/2 transport on SwiftNIO (grpc-swift-nio-transport), in-process transport for tests; "lessons learned from years of use at Apple." Mature enough for production.
- Downsides for this app: requires end-to-end HTTP/2 — corporate proxies/SSL-inspection middleboxes frequently downgrade to HTTP/1.1 or buffer DATA frames, breaking bidi streams (this is why gRPC-Web exists); binary protobuf hurts open-source debuggability vs JSON-over-WS; heavier dependency tree (SwiftNIO + NIOSSL + NIOHTTP2) in the Mac app; no URLSession transport in grpc-swift-2, so you lose OS-level proxy/VPN integration that URLSession provides. Google Cloud STT v2 proves the model works, but Google controls both ends inside GCP networking.

### Chunked HTTP POST up + SSE down
- Fatal flaw upstream: **many proxies/CDNs/load balancers buffer request bodies** until complete, so streamed-request-body POST silently degrades to batch; URLSession streamed uploads (`uploadTask(withStreamedRequest:)` + `needNewBodyStream`) can't tell you how much was actually delivered and don't resume. SSE downstream is proxy-friendly (plain HTTP response) but SSE over HTTP/2 through inspection proxies (Zscaler/Netskope/Palo Alto) is known to die with ERR_HTTP2_PROTOCOL_ERROR and instant CONNECTING→CLOSED transitions (https://github.com/coder/agentapi/issues/204). Verdict: good as *fallback* pattern (single batch POST), wrong as primary.

### WebTransport / HTTP-3 / QUIC
- WebTransport only reached cross-browser Baseline in **March 2026** (Safari 26.4) (https://webkit.org/blog/17862/webkit-features-for-safari-26-4/, https://webrtc.ventures/2026/04/webtransport-is-now-baseline-what-it-means-for-real-time-media/). **No native URLSession WebTransport API on macOS**; you'd hand-roll over `NWProtocolQUIC` (macOS 12+) or a Rust/C library. Server ecosystem still thin; UDP/443 is commonly blocked on corporate networks, requiring an HTTP/2 or WS fallback path anyway. QUIC's 0-RTT resumption is attractive (research: reconnect 256 ms vs 501 ms TCP at 120 ms RTT; 65 ms vs 95 ms at 20 ms RTT) but not worth being the primary today. Zero production STT vendors use it.

### Vendor message-schema details (evidence base)
**Deepgram** (https://developers.deepgram.com/reference/speech-to-text/listen-streaming):
- Params: `encoding` (linear16, linear32, flac, alaw, mulaw, amr-nb/wb, opus, ogg-opus, speex, g729), `sample_rate`, `interim_results`, `endpointing` (default 10 ms), `utterance_end_ms`, `vad_events`, `smart_format`, `keywords`/`keyterm`, `model=nova-3`.
- Server msgs: `Results` (`is_final`, `speech_final`, `channel.alternatives[].transcript/confidence/words[]`), `Metadata`, `UtteranceEnd`, `SpeechStarted`.
- Client control (text frames): `{"type":"KeepAlive"}` every **3–5 s** to beat the **10 s no-data timeout** (else close 1011/NET-0001); `{"type":"Finalize"}` flushes and forces final results; `{"type":"CloseStream"}` = graceful drain-then-close with final metadata.
- Semantics: `is_final:true` = segment text frozen (can occur many times per utterance); `speech_final:true` = pause/endpoint detected; docs warn "Do not use speech_final alone to capture full transcripts" — concatenate is_final segments until speech_final.
- Close codes: 1008+DATA-0000 (undecodable audio), 1011+NET-0000 (server sent nothing in window), NET-0001 (client sent nothing in 10 s), NET-0002 (no audio; KeepAlive resets it). Never send empty `b''` (triggers close) (https://developers.deepgram.com/docs/stt-troubleshooting-websocket-data-and-net-errors).
- Latency guide (https://developers.deepgram.com/docs/measuring-streaming-latency): network 20–200 ms + processing 150–300 ms → total transcript latency 200–500 ms; **"streaming buffer sizes should be between 20 and 100 milliseconds of audio"**; measure latency as audio-cursor minus transcript-cursor using interims only (their start/duration timestamps are not for timing analysis).

**AssemblyAI Universal-Streaming v3** (https://www.assemblyai.com/docs/api-reference/streaming-api/streaming-api):
- `wss://streaming.assemblyai.com/v3/ws?sample_rate=16000&encoding=pcm_s16le`; encodings: `pcm_s16le` (default), `pcm_mulaw`, **`opus`, `ogg_opus`, `aac`**; sample_rate 8000–96000.
- Audio: raw binary frames, **each chunk must be 50–1000 ms**; auth via `Authorization` header or temp `token` query param; 3 h max session; billed on connection-open duration.
- Server: `Begin` {type,id,expires_at,configuration}; `SpeechStarted` {timestamp,confidence}; `Turn` {turn_order, transcript, utterance, end_of_turn, end_of_turn_confidence, turn_is_formatted, words[{text,start,end,confidence,word_is_final}], speaker_label}; `Termination` {audio_duration_seconds, session_duration_seconds}; optional `Heartbeat` every 5 s with realtime_factor.
- Client: binary audio; `{"type":"ForceEndpoint"}` (manual finalize — this is the push-to-talk key-up primitive), `{"type":"Terminate"}`, `{"type":"KeepAlive"}` (only needed if `inactivity_timeout` set), `UpdateConfiguration` mid-session (prompt, keyterms_prompt ≤100 terms, end_of_turn_confidence_threshold default 0.4, min/max_turn_silence default max 1536 ms, mode min_latency|balanced|max_accuracy).
- Context/biasing precedent: `prompt` (≤1750 chars) + `keyterms_prompt` — a good model for your bias-phrase fields.

**Soniox** (https://soniox.com/docs/api-reference/stt/websocket-api):
- First frame = JSON config: `{api_key, model:"stt-rt-v5", audio_format:"auto"|"s16le"..., sample_rate, num_channels, language_hints[], context:{general,text,terms}, enable_endpoint_detection, max_endpoint_delay_ms (500–3000, default 2000), endpoint_sensitivity (-1..1), client_reference_id}`; then binary/base64 audio.
- Responses: `{tokens:[{text,start_ms,end_ms,confidence,is_final,language,speaker}], final_audio_proc_ms, total_audio_proc_ms}`; non-final tokens mutate/disappear; final tokens sent exactly once. Special tokens: `<end>` (endpoint detected), `<fin>` (finalization complete). Control: `{"type":"finalize"}`, `{"type":"keepalive"}` (server kills session after ~20 s without audio). **Graceful close = send an empty WebSocket frame**; server replies `{"finished":true}` then closes. Errors as HTTP-style JSON: 400/401/402/403/408/413 (300-min max)/429/500/503 with error_type + request_id.
- The `final_audio_proc_ms`/`total_audio_proc_ms` pair is a clever server-side latency-telemetry design worth copying.

**Google Cloud STT v2** (https://docs.cloud.google.com/speech-to-text/docs/reference/rpc/google.cloud.speech.v2): gRPC-only bidi `StreamingRecognize`; first `StreamingRecognizeRequest` carries recognizer + `streaming_config` with `StreamingRecognitionFeatures{interim_results, enable_voice_activity_events, voice_activity_timeout{speech_start_timeout, speech_end_timeout}}`; then audio-bytes messages. Responses carry `results[]` with `is_final` + `speech_event_type` (SPEECH_ACTIVITY_BEGIN/END). Streaming sessions are limited (~5 min class limit; the docs also note server auto-closes the stream after voice_activity_timeout). Historical v1 guidance: ~100 ms frames as a good tradeoff.

**OpenAI Realtime transcription** (https://developers.openai.com/api/docs/guides/realtime-transcription): WS (or WebRTC); `session.update` with `{type:"transcription", audio.input:{format:{type:"audio/pcm", rate:24000}, transcription:{model:"gpt-live-transcribe", prompt, keywords, languages, delay: minimal|low|medium|high|xhigh}, turn_detection: server_vad|semantic_vad|null}}`; client sends base64 audio via `input_audio_buffer.append`, ends turn with `input_audio_buffer.commit` (manual commit = push-to-talk analog); server emits `conversation.item.input_audio_transcription.delta` then `.completed`, plus `input_audio_buffer.speech_started/stopped`. Notably ships **base64-in-JSON audio** (higher overhead — an anti-pattern you can avoid since you control both ends).

## 2. Audio on the wire
- **Raw PCM s16le, 16 kHz mono = 256 kbps = 32 KB/s; a 20 ms frame is 640 B, 40 ms is 1280 B, 100 ms is 3200 B.** Every vendor's default/lowest-latency path is raw PCM (Deepgram linear16, AssemblyAI pcm_s16le, Google LINEAR16/explicit-decoding, OpenAI pcm 24 kHz, Soniox s16le). Zero encode latency, zero CPU, trivially debuggable. 32 KB/s upstream is negligible on any link that can sustain a video call.
- **Opus**: 16–32 kbps VOIP-mode mono is transparent-enough for ASR; AssemblyAI (raw `opus` packets or `ogg_opus`) and Deepgram (`opus`, `ogg-opus`) both accept it — proof it doesn't materially hurt accuracy. Algorithmic delay: 20 ms frame + 6.5 ms lookahead = 26.5 ms; encode compute on Apple Silicon is sub-millisecond per 20 ms frame (libopus runs at hundreds× real-time for 16 kHz mono speech; negligible vs network jitter).
- **AVAudioConverter cannot reliably encode Opus on macOS** — Apple's frameworks don't expose an Opus encoder; use libopus via SPM bindings: **alta/swift-opus** (BSD-3, embeds Opus C source as submodule, `Opus.Encoder` working with AVAudioPCMBuffer, proven "multiple 48 kHz Opus channels over 4G on iPhone") (https://github.com/alta/swift-opus), or ybrid/opus-swift xcframework wrapper. If you send raw Opus packets (not Ogg), you must length-prefix or frame them yourself — WS binary frames give you framing for free (1 Opus packet per WS frame, AssemblyAI's `encoding=opus` model).
- **FLAC**: lossless, ~50–60 % of PCM (~130–150 kbps at 16 kHz mono); supported by Deepgram/Google/Soniox; encode is cheap but savings are marginal vs Opus and it complicates the server. Skip.
- **Chunk sizing**: Deepgram: 20–100 ms buffers; AssemblyAI: 50–1000 ms enforced; Google: ~100 ms recommended. Tradeoff: a chunk of N ms adds up to N ms of buffering latency; below ~20 ms, per-frame overhead (WS header 2–8 B + TLS record ~25–30 B + TCP/IP 52 B) and packet rate dominate. **Sweet spot for this app: 20–40 ms frames** (raw PCM 640–1280 B rides well under one MTU); 50 pkt/s at 20 ms is fine on LAN/Wi-Fi.
- Decision: **PCM s16le/16 kHz/mono as the default and debug format; Opus 24 kbps (libopus, VOIP application, 20 ms frames, complexity 9) behind a flag** for constrained/metered networks, negotiated in the session-open message.

## 3. Connection lifecycle for push-to-talk
- **Pre-warm at hotkey-down, keep warm across utterances.** Cold connect = DNS + TCP + TLS 1.3 (1-RTT) + WS upgrade ≈ 3 RTTs plus server session setup. TLS 1.3 resumption (PSK) skips cert verification cost (resumed handshakes cost only ~2.3–2.6 ms CPU); 0-RTT saves ≥82 ms on a 60 ms-RTT LTE path (https://www.thousandeyes.com/blog/optimizing-web-performance-tls-1-3). QUIC reconnect measured 256 ms vs TCP 501 ms at 120 ms RTT; 65 vs 95 ms at 20 ms RTT.
- Practical design: (a) open the WS on app launch and after wake-from-sleep; (b) send app-level `{"type":"keepalive"}` every ~15 s while idle (cheap: a few dozen bytes; also keeps NAT/proxy pinholes open — inspection proxies commonly reap idle tunnels at 30–60 s); (c) additionally re-warm on hotkey-down if state ≠ ready, and treat the first audio frame as the readiness probe; (d) rotate the connection proactively after N minutes to dodge silent middlebox expiry. AssemblyAI bills on open-connection time — since you own the server, idle-open costs you only ~1 socket per user.
- **Never lose audio**: capture thread writes into a client-side **ring buffer keyed by sequence number**; network task drains it. Server acks progress (`ack_seq` piggybacked on partial messages); on drop mid-utterance, reconnect with `resume_session_id` + `first_seq`, re-send everything after the last acked seq. Ring buffer of 60 s of 16 kHz PCM is only 1.9 MB.
- **Batch fallback**: if the WS can't (re)connect within a budget (e.g., 1.5–2 s) or fails twice, POST the whole ring buffer to `POST /v1/transcribe` (multipart or raw octet-stream, same auth) and show a "transcribing…" state instead of live partials. This is also the right path for hostile networks (section 4). Because push-to-talk utterances are short (median a few seconds), batch fallback costs seconds, not failure.

## 4. Hostile-network behavior
- SSL-inspection proxies (Zscaler, Netskope, Palo Alto) MITM wss:// and are documented to break long-lived SSE/H2 streams instantly (readyState 0→2, generic error, indistinguishable from outage) and to kill/buffer streaming bodies (https://github.com/coder/agentapi/issues/204); Socket.IO's WS→long-polling auto-fallback exists precisely for this. WebSockets *usually* pass inspection proxies but may be idle-reaped or have the Upgrade stripped.
- Detection strategy on macOS: `NWPathMonitor` for interface/VPN changes (`path.usesInterfaceType`, `path.status`, `unsatisfiedReason`); captive portal = TLS/connect failure + probe `http://captive.apple.com/hotspot-detect.html` expecting "Success" body; SSL inspection = pin your server's SPKI and treat pin-mismatch as "inspected network" → immediately switch to batch-POST mode via URLSession (which inherits system proxy/PAC settings that Network.framework `NWConnection` does not by default — set `ProxyConfiguration` or fall back to URLSession for proxied environments; check `CFNetworkCopySystemProxySettings`).
- Degradation ladder: (1) WS + PCM on port 443; (2) WS via system proxy (URLSessionWebSocketTask path, accepting its slower failure detection, wrapped in your own 3-s app-level ack timeout); (3) batch POST + polling/SSE for result. Persist the working rung per network (keyed by SSID/interface) so subsequent utterances skip the probing.
- VPN/high-latency links: keep chunks at 40–100 ms, rely on app-level keepalive + your own **ack-based deadman timer** (if no server message for 3–5 s while streaming, declare the socket dead — do NOT rely on URLSession error surfacing, per the silent-drop issue) and reconnect-with-resend.

## 5. Timeouts, retries, instrumentation
- Timeout policy: connect ≤ 2 s then retry once then fallback; per-utterance overall deadline (e.g., 10 s) then batch fallback; finalize-response deadline 2 s after key-up `finalize` before falling back to batch of the ring buffer. Exponential backoff (250 ms → 4 s, jittered) for background re-warm attempts; retry only idempotent ops (session open, resend-after-ack) — audio frames are made idempotent by sequence numbers.
- Instrument client-side (mirror Deepgram's method: audio-cursor X vs transcript-cursor Y; use interims only): **t_first_partial** = first `partial` arrival − first audio frame sent; **t_finalize** = `final` arrival − key-up; **conn_reuse** (warm vs cold), handshake ms, retransmit count, fallback rate. Soniox-style `final_audio_proc_ms`/`total_audio_proc_ms` in server messages lets the client separate server compute from network.
- Realistic expectations (warm WS, PCM, decent Wi-Fi): time-to-first-partial p50 ≈ 250–400 ms (chunk 20–40 ms + network 20–100 ms + server 150–300 ms); end-of-speech→final with explicit client Finalize (no VAD wait): p50 ≈ 200–400 ms, p99 ≤ 1 s. Industry anchors: Hamming.ai over 4 M calls: AssemblyAI Universal-3 Pro 307 ms P50, Deepgram Nova-3 516 ms P50; Pipecat bench: AssemblyAI ~262 ms mean / 355 ms p95 time-to-transcript; Deepgram claims ≤300 ms server-side. Cold-start adds ~100–250 ms (handshakes) — hence pre-warming. Your sub-1 s budget is comfortably achievable; push-to-talk's explicit key-up finalize removes the biggest voice-agent latency (endpoint/VAD wait, which is 100–1500 ms elsewhere).

## Recommended design
**Protocol: raw WebSocket over TLS 1.3 on 443. Client: Network.framework NWConnection+NWProtocolWebSocket primary, URLSessionWebSocketTask secondary (proxy environments), batch HTTPS POST tertiary. Audio: PCM s16le 16 kHz mono in 20–40 ms binary frames; optional Opus 24 kbps via libopus. JSON text frames for control both ways.**

### Message-schema sketch (JSON text frames; audio in binary frames)
Client→server, first frame:
```json
{"type":"session.start","session_id":"uuid","resume":false,
 "audio":{"encoding":"pcm_s16le","sample_rate_hz":16000,"channels":1,"frame_ms":20},
 "language":"en-US","alt_languages":["auto"],
 "context":{"bias_phrases":[{"phrase":"Kubernetes","boost":5}],"prompt":"engineering dictation","app_bundle_id":"com.apple.dt.Xcode","prior_text":"..."},
 "features":{"interim_results":true,"punctuate":true,"smart_format":true,"endpointing_ms":null},
 "client":{"app_version":"1.0","os":"macOS 15.5","net":"wifi"}}
```
Binary audio frame = 4-byte little-endian `seq` + payload (or pure payload with seq implied; explicit seq enables resume). Control: `{"type":"finalize"}` (sent on hotkey-up), `{"type":"keepalive"}` (idle, every 15 s), `{"type":"session.close"}`; resume: `{"type":"session.start","resume":true,"session_id":"...","first_seq":1234}`.
Server→client: `{"type":"session.ready","session_id","max_idle_s":30}`; `{"type":"partial","seq_ack":1290,"text":"hello wor","words":[{"t":"hello","start_ms":0,"end_ms":420,"conf":0.97}],"audio_processed_ms":1680}`; `{"type":"final","utterance_id":1,"text":"Hello world.","formatted":true,"audio_processed_ms":2100,"proc_ms":180}`; `{"type":"error","code":"unsupported_audio|auth|rate_limited|internal","http_status":400,"message":"...","request_id":"...","retryable":false}`; `{"type":"closed","reason":"client_request|idle_timeout"}`. Semantics copied from the field: partials are mutable and replace prior partial for the open utterance (Deepgram/Soniox model); finals are immutable and sent once; server flushes everything and emits `final` within ~300 ms of `finalize`; idle timeout ~30 s reset by keepalive; graceful close = drain then WS close 1000, abnormal = 1011 + error frame first (Deepgram NET-xxxx model).

## KEY FACTS
- All major streaming STT vendors except Google use raw WebSocket: Deepgram wss://api.deepgram.com/v1/listen, AssemblyAI wss://streaming.assemblyai.com/v3/ws, Soniox wss://stt-rt.soniox.com/transcribe-websocket, OpenAI wss://api.openai.com/v1/realtime; Google Cloud STT v2 StreamingRecognize is gRPC-bidi only.
- Universal wire pattern: binary WS frames carry audio, text WS frames carry JSON control/results; Deepgram closes with 1008/DATA-0000 if JSON arrives as a binary frame.
- URLSessionWebSocketTask has a confirmed silent-drop defect: after network loss, send() reports success for 40+ s and the error surfaces only after 60 s-3 min; pings return no pong and no error; Apple DTS recommends Network.framework (NWProtocolWebSocket) instead (developer.apple.com/forums/thread/678384).
- URLSessionWebSocketTask sendPing pongReceiveHandler can be called twice on cancel-during-ping (Apple bug r.129686846), crashing withCheckedThrowingContinuation wrappers; maximumMessageSize defaults to 1 MB; receive() must be re-armed per message.
- grpc-swift-2 shipped 2025-02-14 with async/await bidi streaming over SwiftNIO HTTP/2 (grpc-swift-nio-transport); no URLSession transport, so it bypasses system proxy handling; corporate proxies that downgrade to HTTP/1.1 break gRPC bidi (why gRPC-Web exists).
- Deepgram protocol: KeepAlive text frame every 3-5 s or connection closes after 10 s with 1011/NET-0001; Finalize flushes pending audio to finals; CloseStream drains then closes; is_final=segment frozen, speech_final=endpoint; docs say concatenate is_final segments until speech_final.
- AssemblyAI Universal-Streaming v3: audio chunks must be 50-1000 ms; encodings pcm_s16le (default), pcm_mulaw, opus, ogg_opus, aac; messages Begin/SpeechStarted/Turn/Termination; ForceEndpoint = manual finalize primitive for push-to-talk; prompt <=1750 chars + keyterms_prompt <=100 terms for biasing; 3 h max session billed on connection-open time.
- Soniox: first frame is JSON config (api_key, model stt-rt-v5, audio_format auto, language_hints, context, enable_endpoint_detection, max_endpoint_delay_ms 500-3000); responses are token arrays with is_final plus final_audio_proc_ms/total_audio_proc_ms telemetry; finalize and keepalive control types; ~20 s no-audio kill; graceful close = empty WS frame then {finished:true}.
- OpenAI Realtime transcription sends base64 audio inside JSON (input_audio_buffer.append) at pcm 24 kHz, commit ends the turn, deltas arrive as conversation.item.input_audio_transcription.delta then .completed; base64-in-JSON is measurably wasteful vs binary frames.
- Deepgram official guidance: streaming buffer/chunk sizes should be 20-100 ms of audio; Google's guidance is ~100 ms frames; latency budget = network 20-200 ms + server processing 150-300 ms = 200-500 ms total transcript latency.
- Raw PCM s16le 16 kHz mono is 256 kbps (32 KB/s); a 20 ms frame is 640 bytes; every vendor's default/lowest-latency input is raw PCM, so PCM-first is industry best practice.
- AVAudioConverter cannot reliably encode Opus on macOS; use libopus via SPM: alta/swift-opus (BSD-3, Opus C source as submodule, AVAudioPCMBuffer API) or ybrid/opus-swift; Opus adds 26.5 ms algorithmic delay (20 ms frame + 6.5 ms lookahead) and sub-millisecond per-frame encode cost on Apple Silicon.
- AssemblyAI and Deepgram both accept Opus input (raw packets or Ogg), proving 16-32 kbps Opus does not materially hurt ASR accuracy; FLAC only halves PCM (~130-150 kbps) and is not worth the complexity.
- TLS 1.3 is 1-RTT, 0-RTT resumption saves >=82 ms on a 60 ms-RTT LTE path; resumed handshakes cost only ~2.3-2.6 ms CPU; QUIC reconnect measured 256 ms vs TCP 501 ms at 120 ms RTT; cold WS connect = ~3 RTTs (TCP+TLS+Upgrade).
- SSL-inspection proxies (Zscaler, Netskope, Palo Alto) kill long-lived SSE/H2 streams with instant generic errors indistinguishable from outages (github.com/coder/agentapi/issues/204); Socket.IO's WS->long-polling fallback exists for exactly this; proxies also buffer streamed POST request bodies, ruining chunked-upload streaming.
- WebTransport reached cross-browser Baseline only in March 2026 (Safari 26.4); macOS has no native client API (would need NWProtocolQUIC, macOS 12+); UDP/443 commonly blocked on corporate networks; no STT vendor uses it.
- Latency anchors: Hamming.ai 4M-call benchmark: AssemblyAI Universal-3 Pro 307 ms P50 (8.14% WER), Deepgram Nova-3 516 ms P50 (9.87% WER); Pipecat bench: AssemblyAI ~262 ms mean / 355 ms p95 time-to-transcript.
- Push-to-talk removes VAD/endpoint wait (elsewhere 100-1536 ms): hotkey-up sends an explicit finalize, so end-of-speech-to-final of p50 200-400 ms / p99 <=1 s is realistic on a warm connection.
- Deepgram's latency measurement method: track audio-cursor (seconds sent) minus transcript-cursor (seconds transcribed in interims); vendor start/duration timestamps are explicitly not for timing analysis.
- Network.framework NWConnection does not use system proxy/PAC settings by default (URLSession does), so proxied corporate environments need a URLSessionWebSocketTask or batch-POST fallback path.

## RECOMMENDATIONS
- Primary transport: raw WebSocket (RFC 6455) over TLS 1.3 on port 443 with JSON text frames for control and binary frames for audio - matches Deepgram/AssemblyAI/Soniox production practice, best proxy traversal, best open-source debuggability (wscat-able).
- Client stack: Network.framework NWConnection + NWProtocolWebSocket as the primary implementation (immediate .waiting/.failed states, viabilityUpdateHandler, TCP keepalive control) to avoid URLSessionWebSocketTask's 60s+ silent-drop defect; keep a URLSessionWebSocketTask path for system-proxy/PAC environments; do not use grpc-swift or WebTransport for v1.
- Audio: PCM s16le, 16 kHz, mono, 20-40 ms binary frames (640-1280 B) as default - zero encode latency and every vendor's default; add optional Opus 24 kbps VOIP-mode 20 ms frames via libopus (alta/swift-opus bindings; AVAudioConverter cannot encode Opus) negotiated in session.start for constrained networks.
- Never trust transport-level liveness: implement an app-level deadman timer (no server message within 3-5 s while streaming = dead socket), app-level keepalive every ~15 s at idle, and server acks (seq_ack) piggybacked on partials.
- Push-to-talk lifecycle: keep one warm WS at idle (rotate every few minutes), re-warm on hotkey-down if not ready, enable TLS 1.3 session resumption on the server; utterance end = client sends {type:finalize} on hotkey-up and server must flush finals within ~300 ms (copy Deepgram Finalize / AssemblyAI ForceEndpoint semantics).
- Reliability: capture audio into a sequence-numbered ring buffer (60 s = 1.9 MB) decoupled from the socket; on mid-utterance drop, reconnect with resume:true + first_seq and resend unacked frames; if (re)connect exceeds ~2 s or fails twice, fall back to a single batch POST /v1/transcribe of the ring buffer.
- Hostile networks: detect via NWPathMonitor + captive.apple.com probe + SPKI pin-mismatch (indicates SSL inspection); degradation ladder WS-direct -> WS-via-system-proxy -> batch POST; cache the working rung per network (SSID) so later utterances skip probing.
- Schema: adopt the session.start/partial/final/error/keepalive/finalize JSON schema sketched in the report, with AssemblyAI-style bias fields (bias_phrases + free-text prompt + app context) and Soniox-style server timing fields (audio_processed_ms, proc_ms) for built-in latency telemetry.
