# Research: API access model: auth, key distribution, and abuse prevention for an open-source client of a private hosted STT API
# Client-to-API Access Model for an Open-Source macOS Dictation App

## 1. How existing open-source clients of hosted services handle access

**BYOK dictation apps (closest comps)**
- **VoiceInk** (github.com/Beingpax/VoiceInk, GPL-3.0): default path is fully local (whisper.cpp + Parakeet via FluidAudio on ANE); optional cloud "AI Enhancement" is BYOK (OpenAI/Anthropic/Google/Groq). Keys stored in **iCloud Keychain with sync enabled**. Monetization: source is free to compile; paid license ($25 Solo / $39 Personal / $49 Extended per getvoibe.com/resources/voiceink-pricing/) buys signed builds, auto-updates, support. "Not accepting pull requests… You're welcome to fork." No technical fork protection — the moat is convenience (notarized builds + updates).
- **Superwhisper** (closed source, $8.49/mo–$249.99 lifetime): cautionary tale — stores BYOK API keys **in plaintext JSON under ~/Library/Application Support**, readable by any user-level process, captured in Time Machine/cloud backups; 15+ votes on its UserJot feedback board demanding Keychain storage, unfixed as of Apr 2026 (getvoibe.com/resources/is-superwhisper-safe/). Also saves recordings to iCloud Documents by default (23 votes to make opt-in). These are the exact complaints to design against.
- **Whispering / Epicenter** (github.com/epicenter-so/epicenter, app AGPL-3.0, libs MIT): pure BYOK — "Audio goes from your device to the provider you choose. Epicenter servers are not in that transcription path." Keys stay local. "Revenue is intended to come from hosting and services, not from selling closed licenses." BYOK-only = zero server cost, zero abuse surface, but onboarding requires the user to already own an API key — a huge funnel filter for non-developers.

**CLI/OSS clients of hosted services**
- **gh CLI**: public client, OAuth **Device Authorization Grant (RFC 8628) first, loopback-server web flow as fallback** (pkg.go.dev/github.com/cli/oauth/device). Client ID is embedded and public — "OAuth Client IDs are meant to be visible; device flow doesn't use secrets." Token stored "securely in the system credential store," **plain-text file fallback** if no keyring; `--insecure-storage` flag exists (cli.github.com/manual/gh_auth_login). Scopes: repo, read:org, gist.
- **rclone**: embedded a shared Google OAuth client_id/secret in source for years; secret "obviously not treated as a secret" per Google's own installed-app docs (googleapis.github.io/google-api-python-client/docs/oauth-installed.html). Result: the shared client blew past Google's per-client-ID rate quota (10 QPS global), Google began charging for it, and **rclone is retiring the shared client_id entirely during 2026** — every user must now create their own client_id (rclone.org/drive/, github.com/giuliocsr/rclone4gdrive/issues/6). Lesson: any credential shipped in an open-source client becomes a commons and will be exhausted/abused; plan for per-user identity from day one.
- **Tailscale**: "where the OS is open source, the daemon and GUI are open source; where the OS is closed, the daemon is open source and the GUI is closed" — coordination server is proprietary (tailscale.com/opensource). Auth = client generates node keypair, `tailscale up` opens a browser login URL against the control plane (browser SSO → node registered to account). **Headscale** (github.com/juanfont/headscale) reimplements the control protocol; Tailscale employs its lead maintainer and treats it as ecosystem-positive rather than fighting it. Lesson: open protocol + swappable control-plane URL converts forks from a threat into an ecosystem.
- **Bitwarden / Vaultwarden**: clients GPL, server AGPL + proprietary "Bitwarden License" enterprise dir; **Vaultwarden** reimplements the server API in Rust (AGPL) and unlocks paid features free; official clients work against it unchanged. 2024 controversy: `bitwarden/sdk-internal` license clause restricting use "only for apps compatible with Bitwarden" (alternativeto.net/news/2024/10/...). Lesson: clients must accept a user-configurable server URL; license games on client deps burn community trust.
- **Signal**: server AGPL, but Moxie (LibreSignal issue #37, 2016): "I'm not OK with LibreSignal using our servers, and I'm not OK with LibreSignal using the name 'Signal.' You're free to use our source code… but you're not entitled to use our name or the service that we run." Enforcement is **ToS + trademark, not technical secrets**. This is the standard, defensible posture for an open client + funded hosted service.
- **Zed**: open-source editor; hosted features gated behind **GitHub OAuth (read:user scope only)** browser flow at zed.dev; sign-in optional for local editing (zed.dev/docs/authentication). Firewall complaint threads (zed discussion #40873) show browser-based sign-in fails in locked-down networks — offer a device-code fallback.
- **Codex CLI** (learn.chatgpt.com/docs/auth): browser sign-in with ChatGPT, **loopback callback on port 1455**; creds cached in `~/.codex/auth.json` ("Treat auth.json like a password"); configurable `cli_auth_credentials_store = file | keyring | auto`; headless via `codex login --device-auth` (device-code flow) or SSH tunnel of 1455; API-key alternative `codex login --with-api-key`; auto-refresh of tokens mid-session. Claude Code similarly does browser OAuth and stores credentials in the macOS Keychain. These two are the closest live examples of "browser sign-in → short-lived tokens → expensive hosted inference from an open(ish) client."

## 2. OAuth 2.0 for a native macOS app (no client secret)

- **RFC 8252 (OAuth for Native Apps)**: native apps are public clients; MUST use Authorization Code + **PKCE (RFC 7636)**; MUST NOT use embedded webviews; use the system browser or a platform "secure authentication session."
- **ASWebAuthenticationSession**: macOS 10.15+. On macOS it opens the user's **default browser** (or Safari) — shared cookies mean returning users get one-click SSO. The old `init(url:callbackURLScheme:)` is **deprecated**; use `init(url:callback:completionHandler:)` with `ASWebAuthenticationSession.Callback` (`.customScheme("myapp")` or `.https(host:path:)` — the https form needs Associated Domains, which works for Developer ID apps via the `webcredentials`/`applinks` entitlement + apple-app-site-association). `prefersEphemeralWebBrowserSession` opts out of SSO cookies. Caveat: macOS shows a consent sheet "\"App\" Wants to Use \"yourdomain.com\" to Sign In" before opening.
- **Loopback redirect (http://127.0.0.1:PORT)**: what gh (fallback) and Codex (port 1455) use; avoids the ASWebAuthenticationSession consent sheet, works with any browser, standard for desktop per Google — Google is deprecating loopback only for iOS/Android/ChromeOS client types, "will continue to be supported on desktop apps."
- **Device Authorization Grant (RFC 8628)**: user visits verification_uri, types 8-char code; client polls token endpoint. gh's primary flow; Codex's headless flow. Needed for SSH/remote and firewall-restricted cases; trivial to implement on your own IdP.
- **Sign in with Google from a native Mac app**: use "Desktop app" OAuth client type; client_id public, secret explicitly non-secret; **embedded webviews are blocked** (`disallowed_useragent` error) — must use system browser/loopback; OOB (`urn:ietf:wg:oauth:2.0:oob`) is dead. Gotchas: OAuth consent screen in "Testing" status issues refresh tokens that expire in 7 days; ~100 refresh tokens per Google Account per client_id (oldest silently revoked) — matters for multi-device; app verification review needed once past 100 users. Better architecture: do Google sign-in **on your website**, not in-app — the app only ever talks to *your* IdP, so Google is an implementation detail server-side.
- **Sign in with Apple**: entitlement `com.apple.developer.applesignin` lists macOS 10.15+, but it requires a provisioning profile, and support in **Developer ID** profiles is not clearly documented (community reports are mixed). The reliable path for a non-App-Store Mac app is **Sign in with Apple JS/REST via the web** (Services ID + redirect to your domain), again pushed to your website/IdP rather than native ASAuthorizationController. Flag: verify Developer ID support before committing to the native button.
- **Your own IdP (recommended)**: mint **short-lived JWT access tokens (5–15 min) + rotating refresh tokens with reuse detection** (OAuth 2.0 Security BCP, RFC 9700), refresh-token-per-device so revocation is per-device, RFC 7009 revocation endpoint, and a "devices" page in the web account portal (Tailscale-style machine list). For streaming, pass the JWT in the WebSocket handshake (`Authorization` header or first message) and re-auth on reconnect.

## 3. Anonymous / trial access + attestation reality on macOS

- **Attestation on macOS is weak**: `DCAppAttestService.isSupported` **returns false on all Mac forms** — native macOS apps, Mac Catalyst, iOS-on-Apple-silicon (developer.apple.com/documentation/devicecheck/dcappattestservice/issupported). So App Attest is off the table. **DCDevice (DeviceCheck)** is nominally macOS 10.15+ (2 server-readable bits per device + Apple-verified device token, verified server-side against Apple's API with your DeviceCheck key) — the only Apple-backed device signal for a Developer ID app, but it needs a registered App ID and real-world reliability for Developer ID-signed apps should be prototyped early (see open questions). Firebase App Check wraps DeviceCheck/App Attest + supports custom providers and limited-use tokens, but inherits the same platform limits.
- **Consequence**: an anonymous device token on macOS is **self-asserted** (any fork/script can mint "devices"). Treat the free tier as a marketing cost with an abuse ceiling, not a security boundary.
- **Token-vending design** (Firebase Anonymous Auth pattern): first-run `POST /v1/device` → opaque `device_token` stored in Keychain; server tracks quota per token. Gate issuance with **Cloudflare Turnstile** on a lightweight web page (the app opens it in ASWebAuthenticationSession/browser once at install) — Turnstile is a free CAPTCHA-alternative with server-side `siteverify`, embeddable on any site (developers.cloudflare.com/turnstile/). Add IP-based issuance rate limits and velocity checks.
- **Quota shapes in the wild**: Wispr Flow free = **2,000 words/week on desktop** (1,000/week iPhone, unlimited Android), Pro $15/mo ($12 annual), no credit card for free tier (wisprflow.ai/pricing). OpenRouter free models: **50 requests/day** (<$10 lifetime credits) → 1,000/day (≥$10), plus 20 req/min (openrouter.ai/docs/api-reference/limits). A recharging word budget (e.g., 2,000 words/week, resets weekly) matches category norms and is easy to message in UI.
- **Abuse economics for STT**: dictation is self-limiting — humans speak ~130–160 wpm, so an honest push-to-talk user consumes ≤ ~10k words/hour. Abuse = using your endpoint as a **free batch transcription farm** (uploading podcasts/YouTube audio faster than realtime). Cheap, effective server-side controls: (a) accept audio only as a **realtime stream at ≤1–2× realtime factor** per connection; (b) 1 concurrent stream per device/account; (c) max utterance length (e.g., 5 min) — push-to-talk never needs more; (d) word/audio-second quotas per device AND per account AND per IP; (e) global circuit breaker per anonymous cohort. Cost anchor: commodity hosted Whisper is ~$0.006/min (OpenAI whisper-1) and Groq-class inference is under $0.001/min, so even 1M free-tier minutes/month is low-thousands of dollars — quota + realtime-factor caps keep worst-case bounded without attestation.

## 4. Secure client-side credential storage (macOS Keychain)

Per **TN3137** (developer.apple.com/documentation/technotes/tn3137-on-mac-keychains):
- Use the **SecItem API** targeting the **data protection keychain**: `kSecClass: kSecClassGenericPassword`, **`kSecUseDataProtectionKeychain: true`** (safe to set unconditionally cross-platform). File-based keychain (SecKeychain) is deprecated (`SecKeychainCreate` deprecated macOS 12) and has the ACL/prompt model users hate.
- Access control in the data protection keychain is **entitlement-based (keychain-access-groups from the provisioning profile)**, not ACL-prompt-based: items are readable by apps sharing the access group (`TEAMID.bundle.id`). Across normal app updates signed by the same Team ID, access persists silently. A **fork signed by a different team cannot read the official app's items** — good default isolation. Ad-hoc/unsigned local builds can't use data protection keychain access groups (need an app-like bundle + provisioning; TN3137's "Signing a daemon with a restricted entitlement") — fall back to `kSecUseDataProtectionKeychain: false` or file storage for unofficial builds.
- Accessibility: `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` for refresh/device tokens if you ever refresh in background agents; `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` otherwise. Use `ThisDeviceOnly` unless you deliberately want iCloud Keychain sync (`kSecAttrSynchronizable: true` — VoiceInk syncs BYOK keys this way; nice for multi-Mac BYOK, but widens blast radius).
- Never store the access JWT — it's short-lived, keep in memory. Persist only the rotating refresh token / device token.
- Failure modes to avoid, all shipped by real competitors: Superwhisper's plaintext JSON in Application Support; gh's plaintext `hosts.yml` fallback; Codex's default `auth.json` file (docs literally warn "treat like a password"). For BYOK keys specifically: Keychain, never UserDefaults/plist/JSON, and show the item under a clear service name (e.g., "YourApp — API Credentials").

## 5. BYOK / self-host escape hatch without divergence

- Ship one client code path: a single `SpeechBackend` config = `endpoint URL + credential provider`. Official builds default to `api.yourapp.dev` + OAuth/device-token auth; a Settings field (or config file/defaults key, like rclone's `client_id` option and Bitwarden's self-hosted server URL) points at a self-hosted server or BYO provider key. Whispering proves BYOK-in-Keychain UX; Vaultwarden/Headscale prove that a **published, stable wire protocol** is what keeps forks compatible instead of hostile.
- Open-source a **minimal reference server** (even a thin proxy over whisper.cpp/faster-whisper that speaks your exact REST/WS contract). Then "self-host" and "hosted" are the same protocol and can't diverge; your hosted advantage is accounts, quota, model quality, and ops — the Tailscale/Bitwarden moat, not secrecy.
- Legal layer: permissive-or-GPL client license + **trademark policy** (Signal precedent: forks may not use your name or your hosted servers) + ToS stating the hosted API is for official builds/registered clients. Enforcement is quota + revocation, not embedded secrets — nothing in the binary is secret, by design.

## Candidate end-to-end access models

**Model A — Anonymous device token with recharging word quota (frictionless trial)**
Onboarding: launch → mic + accessibility permissions → dictate immediately. First run silently does `POST /v1/device` (optionally after a one-time Turnstile page) → device_token in Keychain → server grants e.g. 2,000 words/week (Wispr Flow parity). Server components: device registry, quota/token-bucket store (Redis), STT gateway with realtime-factor + concurrency caps, IP rate limiter. Abuse posture: weakest — tokens are mintable by scripts since macOS has no App Attest; bounded by issuance throttling + quotas + realtime caps; acceptable because STT is cheap per minute. Fork behavior: forks can vend tokens too unless you gate issuance (Turnstile + ToS + per-IP caps); revoke abusive cohorts server-side.

**Model B — Browser sign-in → short-lived JWT → streaming API (sustained/paid use)**
Onboarding: "Continue with Google / Apple / email" button → ASWebAuthenticationSession (or loopback server, gh/Codex-style; add RFC 8628 device-code fallback for restricted networks) → your IdP handles Google OIDC / Sign in with Apple JS on the web side → app receives auth code (PKCE) → rotating refresh token (per-device) in data-protection Keychain → 10-min JWTs minted for each WS/streaming session. Server: IdP/OAuth server (or Auth0/Clerk/Firebase Auth/Supabase to start), token service, account+quota DB, devices page with per-device revoke, STT gateway validating JWTs statelessly. Abuse posture: strong — quota per verified account, sign-up friction deters farming, per-device revocation, reuse-detection kills stolen refresh tokens. Fork behavior: forks can present your sign-in only if you let them; ToS + client registration + trademark (Signal model) is the enforcement, and it's enough in practice.

**Model C — BYOK-only (Whispering model)**
No server at all: user pastes an OpenAI/Groq/Deepgram key or a self-hosted endpoint; keys in Keychain. Zero cost, zero abuse, zero accounts — but onboarding excludes non-developers and you learn nothing about usage; no revenue path except VoiceInk-style paid convenience builds.

## Recommendation

Ship **A + B layered, with C as the permanent escape hatch** (exactly the composite the market leaders converge on): anonymous Keychain device token with a 2,000-words/week recharging quota for instant first-run magic; a "sign in to keep going" upsell that upgrades the device record to an account (merge quota, multi-Mac); short-lived JWTs over the streaming API; rotating refresh tokens in the data-protection Keychain (`kSecUseDataProtectionKeychain`, `AfterFirstUnlockThisDeviceOnly`, non-synchronizable); loopback-redirect browser flow primary (Codex-style, port pinned) with RFC 8628 device-code fallback; server-side realtime-factor + concurrency + utterance-length caps as the real abuse control; a documented REST/WS protocol + reference self-host server + Settings endpoint override so forks and self-hosters are first-class; trademark policy + ToS reserving the hosted service for official builds. Do NOT: embed any shared provider credential (rclone's 2026 retirement), store anything in plaintext JSON (Superwhisper), or depend on App Attest (unsupported on Mac).

## RECOMMENDATIONS
- Layer the access model: anonymous Keychain-stored device token with a recharging quota (2,000 words/week, Wispr Flow parity) for zero-friction first run, then 'sign in to keep dictating' which merges the device into an account with higher/paid quota — plus a permanent BYOK/self-host endpoint override in Settings
- Run your own IdP boundary: do Google OIDC and Sign in with Apple (JS/web) on your website, and have the app only ever exchange codes with api.yourapp.dev — avoids Google refresh-token limits, Apple Developer ID entitlement uncertainty, and lets you add providers without client releases
- Native flow: Authorization Code + PKCE via loopback 127.0.0.1 redirect (Codex/gh style, avoids the ASWebAuthenticationSession consent sheet and works with the default browser), with an RFC 8628 device-code fallback for firewalled/SSH users; short-lived (~10 min) JWTs presented on WebSocket connect, rotating per-device refresh tokens with reuse detection, and a web 'devices' page for per-device revocation
- Storage: SecItem with kSecUseDataProtectionKeychain=true, kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly, non-synchronizable, for refresh/device tokens and BYOK keys; keep access JWTs in memory only; never write credentials to JSON/UserDefaults (Superwhisper's documented failure); handle errSecMissingEntitlement gracefully for unsigned fork builds
- Do not rely on device attestation for the free tier — App Attest is unsupported on Mac; at most prototype DCDevice, and gate anonymous token issuance with Cloudflare Turnstile on a one-time web page plus per-IP velocity limits, treating trial abuse as bounded marketing cost
- Make abuse control server-side and physical: accept audio only as a stream at ≤1-2x realtime per connection, 1 concurrent stream per device/account, ~5-minute max utterance, word quotas per device+account+IP, global anonymous-cohort circuit breaker — these bound worst-case GPU cost regardless of client forgery
- Never embed any shared upstream credential (API key, OAuth client secret) in the open-source client — rclone's 2026 shared-client retirement is the proof; everything in the binary must be assumed public
- Publish the REST/WS speech protocol and ship a minimal open reference server (thin proxy over whisper.cpp/faster-whisper speaking the same contract) so self-host and hosted never diverge — Headscale/Vaultwarden model; official-build value = accounts, quota, model quality, notarized updates (VoiceInk model)
- Adopt the Signal legal posture from day one: permissive/GPL code + explicit trademark policy + ToS reserving the hosted API for official builds; enforce with quotas and token revocation, not client secrets
- Instrument for abuse from launch: per-token realtime-factor and words/day metrics, issuance-per-IP dashboards, and a kill switch per client version (minimum supported build) since you cannot trust client-side gates in an open-source app
